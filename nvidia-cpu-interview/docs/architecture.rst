Arm、CPU 与 SoC 体系结构
==========================================

从一次 CPU load 开始，说明它怎样经过地址翻译和缓存层次访问内存。再把发起者换成设备，画出设备地址、互连和内存控制器的位置。这两张图能检验你是否真正理解“贴近硬件”。

两条地址路径
----------------------------

.. code-block:: text

   CPU 虚拟地址  →  MMU / TLB        →  物理地址  →  内存
   设备 DMA 地址 →  IOMMU（若启用） →  物理地址  →  内存

这是地址关系的概念图。TLB 缓存翻译结果，数据缓存保存缓存行，两者的失效操作解决不同问题。DMA 地址由映射接口返回，不能从用户态指针或 CPU 虚拟地址猜出。无 IOMMU 的系统也可能有总线地址转换或 DMA 地址范围限制。 `Linux DMA 地址示意与约束 <https://docs.kernel.org/core-api/dma-api-howto.html>`_

* **CPU 基础。** 能解释指令、流水线、乱序执行、分支预测和访存延迟各影响什么。区分吞吐量与单次延迟。给出一次测量，说明工作集、核绑定、频率、预热和采样计数会如何影响解释。
* **缓存与多核。** 理解缓存行、写回、共享缓存、一致性与伪共享。两个核写同一缓存行上的不同计数器，可能因所有权反复转移而变慢。用分离缓存行的布局做对照，同时核对工作量和绑核策略。
* **内存序。** 缓存一致性解决对同一位置的观察，不自动保证不同位置之间的发布顺序。能解释 acquire/release。进阶时说明 DMB 约束特定访问的观察顺序、DSB 涉及相应操作完成、ISB 使后续取指反映相关上下文变化。选择原语要看观察者、共享域和设备协议。 `Arm 内存模型 <https://documentation-service.arm.com/static/62a304f231ea212bb662321d>`_ · `Linux 内存屏障 <https://docs.kernel.org/core-api/wrappers/memory-barriers.html>`_
* **AArch64 与异常。** 能读常见 load/store、分支、栈帧与返回地址。理解 EL0 用户态、常见 EL1 内核、EL2 虚拟化及 EL3 固件角色。遇到同步异常，结合故障指令、ESR_EL1 的异常类别和 FAR_EL1 中有效的故障地址判断下一步。中断由 GIC 等控制器路由。 `Arm 异常模型 <https://documentation-service.arm.com/static/67ac57fb091bfc3e0a9479cc>`_
* **SoC 集成。** 能在框图中指出 CPU、内存控制器、互连、DMA 主设备、中断控制器、时钟、复位与电源域，并说明某一域未开启会让哪项观测失去意义。

自测与解题提示
----------------------------

**两个核传消息，接收方看到了 ready，却读到旧的 payload。为什么？** 先说明缓冲区是否复用、访问是否有数据竞争。如果是普通 RAM 上的 CPU 线程，检查所有权与 release/acquire 是否正确配对。如果观察者是设备，换成 DMA 映射、缓存同步与 I/O 顺序规则。说明你的修复适用哪一条路径。

**工作集翻倍后变慢，如何区分缓存缺失、TLB 缺失和带宽饱和？** 固定线程数、核与访问模式，分别改变工作集、页大小或并发流数。记录耗时与平台支持的 PMU 事件，核对计数是否复用、频率是否变化。单个 miss 计数不足以证明瓶颈。
