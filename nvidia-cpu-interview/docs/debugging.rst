系统排障与根因验证
==========================================

收到“高负载时偶发超时”的报告，先确定预期结果、实际结果、影响范围和最小触发条件。下面的时间线是教学数据，来自同一软件单调时钟。不同设备时钟需要额外的同步证据才能直接比较。

一次超时可能有三个起点
---------------------------------------

.. code-block:: text

   0.000 ms   submit       req=42  queue=1
   0.020 ms   doorbell     req=42  queue=1
   4.000 ms   wait_timeout req=42  queue=1
   4.120 ms   irq_entry            queue=1
   4.140 ms   complete     req=42  queue=1

软件记下的 IRQ 入口晚于超时。单凭这段记录无法判定设备执行慢，还是设备早已完成、CPU 迟迟没服务中断。doorbell 日志本身也不能证明写入已经到达设备。

.. list-table::
   :header-rows: 1
   :widths: 30 38 32

   * - 待检验的判断
     - 再取一份什么证据
     - 可区分的结果
   * - 设备执行慢或请求未到达
     - 查看超时点可安全读取的队列头、完成项和设备状态，核对状态是否有读清等副作用
     - 设备若已发布目标完成项，应转查通知路径
   * - 通知已发出但处理延迟
     - 将设备状态与 IRQ、屏蔽区间、CPU 负载的 trace 对齐，比较有无压力的样本
     - 设备完成到处理程序入口之间的延迟随压力变化
   * - 软件完成匹配或唤醒有误
     - 关联请求编号、槽位代次、完成发布时间、唤醒与实际调度时刻
     - 中断与完成均及时，但匹配错误或等待线程运行很晚

第一轮先约定同一版本、负载、板型和超时阈值。选择一个能让假设产生不同预测的实验。增加日志可能改变时序，必要时使用窄范围事件或计数器复验。验证修复时，恢复原始频率、负载和日志级别，对比失败数 / 运行次数以及延迟分布。 `Linux 事件跟踪 <https://docs.kernel.org/trace/events.html>`_

根据问题选择工具
---------------------------------------

* **崩溃或卡死。** 用串口、dmesg、异常寄存器和调用栈找第一处异常。核对内核构建、符号文件和模块版本，再用 GDB、addr2line 或 objdump 对应到指令。记录 fault address 是否有效、出错上下文和锁的持有关系。
* **时序与性能。** 用 ftrace / tracepoint 查中断、工作项和唤醒的先后，用 perf 和可用的 PMU 事件看处理器时间花在哪里。读取 /proc/interrupts 能看到累计计数，单次请求需要另外关联。 `ftrace 指南 <https://www.kernel.org/doc/html/latest/trace/ftrace.html>`_
* **早期板级问题。** 若系统尚未启动到日志可用阶段，从启动串口与固件阶段标记切入。若实验室提供 JTAG、示波器或逻辑分析仪，说明要观察哪条复位、时钟或外设信号，以及哪种结果会推翻当前判断。
* **版本回归。** 比较已知好坏组合，固定板卡与输入，再单独切换驱动、固件或配置。使用 git bisect 前先验证判定条件足够稳定。对共享代码的修改补上老平台回归。

自测与解题提示
---------------------------------------

**每次加日志问题就消失，下一步做什么？** 把日志涉及的延时、锁和 MMIO 读回分别看作可能改变行为的因素。设计单变量对照，保留无日志基线。若日志读取了具备副作用的寄存器，先确认该读取究竟改变了什么。

**硬件组无法复现，你怎么交接？** 给出版本、板号、最小命令、失败率分母、成功与失败的同类样本、第一处分歧和下一个需要测量的硬件状态。清楚标出已证实的结论、待验证的猜测，以及谁能拿到缺失的证据。
