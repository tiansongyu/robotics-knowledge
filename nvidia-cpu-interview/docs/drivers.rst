设备驱动与硬件接口
==========================================

白板题可以从一页假想寄存器规格开始。设备有命令队列、启动寄存器和完成中断。你要写出一次提交怎样成功，也要说明如果它永远没有完成，谁来回收资源。

读规格时要找的约束
----------------------------

* **MMIO。** 查访问宽度、大小端、寄存器偏移、保留位、读写副作用和上电默认值。写 1 清除（W1C）的状态位若用常规读改写，可能顺手清掉其他待处理位。Linux 中常用 ioremap 系列建立映射，再按语义选 readl/writel 等访问器。设备要求冲刷 posted write 时，要选规格允许安全读取的位置。 `Linux 设备 I/O 访问 <https://docs.kernel.org/driver-api/device-io.html>`_
* **DMA。** 了解 DMA mask、描述符、环形队列和 scatter-gather。说明 coherent 分配与 streaming 映射的使用情形，检查映射失败、方向和所有权转换。coherent 缓冲区仍可能需要屏障来约束描述符字段的发布顺序。 `Linux DMA 映射指南 <https://docs.kernel.org/core-api/dma-api-howto.html>`_
* **发现与初始化。** 在平台设备案例中，从设备树或固件描述找到寄存器、IRQ、时钟、复位和电源依赖。在 PCIe 案例中，从枚举、BAR、DMA 能力和 MSI/MSI-X 等资源切入。根据设备类型选择一条你能讲透的路径。 `平台设备 <https://docs.kernel.org/driver-api/driver-model/platform.html>`_ · `PCI 驱动 <https://docs.kernel.org/PCI/pci.html>`_

白板练习：提交一笔请求
-----------------------------------

1. **准备。** 确认设备可用、队列有空间，建立映射，填写描述符地址、大小和请求标识。此时记录资源的所有者。
2. **发布。** 按 DMA 和平台协议同步数据、发布所有权，再写 doorbell 通知设备。解释此处需要约束的两次操作、观察者是谁。仅在纸上写一句“加内存屏障”还缺少这两个条件。
3. **完成。** 读取中断来源与完成记录，匹配请求，处理设备状态，并按规格确认中断。数据对 CPU 可见且状态发布后，才能通知上层并归还资源。
4. **超时。** 先保留故障现场。软件等待超时并不代表设备已停止 DMA。确定取消、队列排空或复位协议何时保证设备停用该缓冲区，再回收映射与内存。处理迟到、重复完成以及新的同槽位请求。
5. **关闭与恢复。** 挡住新提交，停设备并同步中断、工作队列和在途请求，再释放资源。失败中途要逆序解开已获取的依赖。devm 系列可代管资源寿命，设备停机和在途回调仍需显式设计。 `Linux 设备资源管理 <https://docs.kernel.org/driver-api/driver-model/devres.html>`_

追问
----------------------------

**规格只给了完成槽位号，没有请求代次。超时后能立即复用同一个槽位吗？** 如果旧完成事件可能迟到，新旧请求就不可区分。检查硬件有无可靠的取消确认、排空、复位完成保证，或在确认旧事件消失前隔离槽位。仅给软件变量加代次不能补出硬件没有返回的信息。

**为什么第一次 probe 成功，休眠恢复后的第一次传输却超时？** 先列出恢复时要重新建立的状态，如时钟、复位、队列基址、IRQ 屏蔽和地址映射。比较冷启动成功样本与恢复失败样本，找出第一次分歧。把恢复后首笔 I/O 纳入回归。
