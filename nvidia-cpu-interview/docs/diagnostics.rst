诊断软件与测试设计
==========================================

测试失败时，下一位工程师需要知道触发条件、哪一层已被排除、下一次该量什么。岗位要求从开发到维护都对驱动和测试负责。 `NVIDIA 职位职责 <https://nvidia.wd5.myworkdayjobs.com/en-US/NVIDIAExternalCareerSite/job/China-Shenzhen/Senior-System-Software-Engineer--CPU_JR2025929>`_

给 CPU 子系统设计一个测试
---------------------------------------

假设目标是发现不同 CPU 核交换数据时的异常。先写出五项约定，再考虑增加压力。

.. list-table::
   :header-rows: 1
   :widths: 22 78

   * - 约定
     - 举例
   * - 可判断的结果
     - 生产者按序号生成已知数据，消费者校验序号、长度与内容。若是多轮测试，消费者确认读完后，生产者才复用该缓冲区。
   * - 变量和对照
     - 固定同步协议、随机种子及工作量，分别跑同核、跨核、小工作集、大工作集。逐项改变核组合或负载，保留可重跑的命令。
   * - 失败分类
     - 区分数据不符、等待超时、测试环境缺失和主动跳过。先验证测试程序自身满足语言内存模型。超时前保存上下文。
   * - 现场与报告
     - 记录平台和固件版本、核号、测试参数、失败轮次、预期值与实测值。性能题补充分布、频率和次数，记录任何观测开销。
   * - 结论边界
     - 测试通过只说明给定条件下未观测到失败。若要归因缓存、一致性或互连，再设计能区分它们的实验。

从单元测试到板级回归
---------------------------------------

用主机端单元测试覆盖参数校验、状态机、编码解码；用 KUnit 验证可隔离的内核逻辑，用 kselftest 从用户态验证内核接口。仿真可重复特定事件顺序，板级测试补上实际 DMA、中断、功耗状态和时序差异。跨板型、芯片版本和固件版本保留已知良好基线。按运行成本安排提交前的短测与夜间长稳，并给每个失败分配可追踪的复现条件。 `KUnit <https://docs.kernel.org/dev-tools/kunit/index.html>`_ · `kselftest <https://docs.kernel.org/dev-tools/kselftest.html>`_

动手练习：迟到的完成事件
---------------------------------------

下载 :download:`completion.c <examples/completion.c>` 。它用普通 C 模拟一个槽位，假定设备能在完成事件里原样返回唯一请求编号。程序按固定顺序投递事件，模拟 A 超时、槽位交给 B、A 的完成才到达。每个检查失败都会打印期望和实测值，并以非零状态退出。

在有 C11 编译器的 Linux 或 macOS 上，在下载目录运行：

.. code-block:: sh

   cc -std=c11 -Wall -Wextra -Werror completion.c -o completion
   ./completion

预期末行是 ``PASS: 4 checks`` 。先读输出，再找出是哪一个判断保护了 B。把请求编号判断里的 != 临时改成 ==，重新编译运行。第一个失败的检查应当是 reject late A。练习在主机内存中运行，真实并发、DMA 可见性和复位时序需要在对应环境验证。

**自测：如果设备只返回槽位号，怎么改？** 列出可依赖的硬件保证，如停机并排空后才复用槽位，再为这个前提设计一个负向用例。如果设备仍能写旧内存，过滤完成事件只保护软件状态，缓冲区寿命还需要单独处理。

**自测：修复前万次出一次错，修复后跑一百次全绿，能宣布修好吗？** 说明原故障的触发条件、两组测试暴露的机会是否相当、是否有能稳定触发的定向用例。给出重复次数、观察时长、覆盖到的板型与剩余风险。把可重复的失败固化为回归。
